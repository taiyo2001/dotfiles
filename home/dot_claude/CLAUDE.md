# Global User Rules

## ツール呼び出しの並列化 (応答速度・トークン削減のため)

独立したツール呼び出しは**必ず 1 メッセージで並列発行**する。順次発行は依存関係がある時だけ。順次に分けるとターン数が増え、毎ターン会話 context が再送されるためトークンも余分にかかる。

### 並列化すべきケース (具体例)

- 複数ファイルの Read (内容を比較・俯瞰したいとき)
- Read + Bash の `git status` / `git diff` / `git log` を同時取得
- 異なる grep パターン・異なるディレクトリでの探索
- 複数の WebFetch / WebSearch
- 独立した複数の Agent サブタスク

### 順次にすべきケース

- ツール B の入力にツール A の出力が必要 (例: grep で見つけたパスを Read)
- 編集系 (Edit/Write) は競合回避のため順次が安全
- 前の結果次第で次の判断が変わる調査

### 判定手順 (実行前に毎回)

1. これから呼ぶツール群をリストアップ
2. 各々が「他の結果を待たずに実行できるか」をチェック
3. Yes のものはすべて 1 メッセージにまとめる

「とりあえず 1 つ呼んでから次を考える」は禁止。先に計画してまとめて発行する。

## トークン消費の節約 (常時意識する)

トークン量が積み上がる主要因は「長い会話 context が毎ターン丸ごと送信されること」「Opus を常用すること」「メイン会話に大量の grep/Read 結果を載せること」の 3 つ。以下を常に実践する。

### 1. タスク切り替え時は `/clear` を提案する

- ユーザーが**明らかに別タスクへ移った**と判断できる場面 (前タスクが完了 / 話題が変わる / コミット・PR 作成が終わった等) では、応答の末尾で「次のタスクに移る前に `/clear` を推奨します」と一言添える。
- `/compact` ではなく `/clear` を勧める。compact は要約コストがかかる上、要約自体が以降毎ターン送信されてコストが続く。区切りがついたら clear。
- ただし**しつこく勧めない**。同一セッション内で一度勧めて流された場合は再提案しない。

### 2. モデル使い分けの提案

- ユーザーが Opus で**単純作業** (典型的な調査・小修正・コミット作業・PR 作成・ドキュメント更新) を始めた場合、最初の応答で「この作業は Sonnet/Haiku でも十分です。`/model` で切り替えると安価になります」と一度だけ提示する。
- Opus を維持すべき作業: 設計判断・複雑なデバッグ・大規模リファクタ・難しいレビュー。これらでは提案しない。
- 判断に迷う場合は提案しない (誤誘導を避ける)。

### 3. 調査系タスクは原則 Subagent (Explore / general-purpose) に委譲する

- **調査・コードリーディング・現状把握フェーズは原則すべて Subagent に投げる**。メインで grep / find / Read を連打しない。
- 具体的な発動条件:
  - 「現状どうなっているか」「どこにあるか」「どう実装されているか」を確認する系のタスク全般
  - 2 ファイル以上を横断して読む / 比較する必要がある場面
  - grep / find を 2 回以上打ちそうな場面 (打ってから判断ではなく、打つ前に Subagent 化)
  - PR / Issue / Design Doc を読んで実装計画を立てる前段の調査
- 理由: メイン会話に grep ヒット全文や複数ファイルの中身が残ると、以降毎ターン再送されてコストが累積する。Subagent は要約のみ返すので context が肥大化しない。
- 直接実行して良い例外: 編集対象が判明済みファイル 1 つで、1〜2 回の Read / Edit で完結する場面のみ。「とりあえず 1 つ見てから次を決める」は禁止 (それは複数回になる前提なので Subagent 化する)。
- Subagent への指示は「何を調べて何を報告するか」を具体的に書く。読ませるパス・grep キーワード・報告フォーマット (Markdown / 文字数上限) まで指定する。

### 4. ファイル読み込みの肥大化を防ぐ

- 大きいファイルは `Read` の `offset` / `limit` で必要箇所のみ読む。「とりあえず全文 Read」をしない。
- `cat` / `head` で長大な出力をメインに流さない (Bash 経由でも context に乗る)。
- ログやデータの貼り付け確認が必要な場合はファイル経由で渡してもらい、必要部分のみ Read する。

### 5. Workflow / 大規模 Agent fan-out は明示指示時のみ

- `Workflow` ツールや多数の並列 Agent は 1 回で数十万トークン消費しうる。ユーザーが「ultracode」「workflow で」「並列で」等を**明示した時のみ**起動する。
- 自動判断で起動しない。便利そうでも単発タスクには使わない。

### 適用上の注意

- これらの提案は**応答の主目的を邪魔しない範囲で**短く添える。応答本体より長い節約アドバイスを書かない。
- ユーザーが「節約モードで」「コスト気にして」等を明示した場合は、上記をより積極的に発動 (Subagent 委譲を増やす / モデル提案を強める)。
- ユーザーが明示的に「Opus のままで」「全部読んで」等と指示した場合はその指示を優先する。
