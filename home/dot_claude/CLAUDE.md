# Global User Rules

## ツール呼び出しの並列化

独立したツール呼び出しは**必ず1メッセージで並列発行**する。順次発行はターン増と、毎ターンのcontext再送によるトークン浪費を生む。

- **並列可**: 複数ファイルのRead比較、Read+`git status`/`diff`/`log`の同時取得、異なるgrepパターン/ディレクトリでの探索、複数のWebFetch/WebSearch、独立した複数Agentサブタスク
- **順次必須**: 後続ツールの入力に前の出力が要る場合(例: grepで見つけたパスをRead)、Edit/Writeなど編集系(競合回避)、前の結果次第で次の判断が変わる調査

判定: 呼ぶツール群を先にリストアップし、他の結果を待たず実行できるものは全て1メッセージにまとめる。「1つ呼んでから次を考える」は禁止。

## トークン消費の節約

主因は「長い会話contextの毎ターン再送」「Opus常用」「grep/Read結果の生載せ」。以下を常に実践する。

1. **`/clear`の提案**: 話題転換・タスク完了などの節目で応答末尾に一言添える。要約コストが以後も残り続ける`/compact`より`/clear`を優先。同一セッションで一度流されたら再提案しない。
2. **モデル使い分けの提案**: Opusで単純作業(調査・小修正・コミット・PR作成・ドキュメント更新)を始めたら最初の応答で一度だけ`/model`でのSonnet/Haiku切替を提示。設計判断・複雑なデバッグ・大規模リファクタ・難しいレビューでは提案しない。判断に迷う場合も提案しない。
3. **調査はSubagentへ委譲**: 現状把握、2ファイル以上の横断読み、grep/findを2回以上打ちそうな場面(打つ前に判断)、PR/Issue/Design Doc読解からの計画立案は原則Subagentに投げる。メインでgrep/find/Readを連打しない。理由: 生の検索結果がcontextに残ると毎ターン再送されコストが累積するが、Subagentは要約のみ返す。例外: 対象ファイルが1つに確定していてRead/Editが1〜2回で完結する場合のみ直接実行可。Subagentへの指示には調べる内容・読ませるパス/キーワード・報告フォーマット(Markdown/文字数上限)を具体的に書く。
4. **ファイル読み込みの肥大化を防ぐ**: 大きいファイルは`Read`の`offset`/`limit`で必要箇所のみ読む。`cat`/`head`で長大出力をメインに流さない。ログ/データの確認はファイル経由で渡してもらい、必要部分のみ読む。
5. **Workflow/大量Agent fan-outは明示指示時のみ**: 「ultracode」「workflowで」「並列で」等の明示がある時だけ起動する。便利そうでも単発タスクには使わない。

節約提案は応答本体より長くしない。「節約モードで」等の明示があれば上記をより積極的に適用し(Subagent委譲を増やす/モデル提案を強める)、「Opusのままで」「全部読んで」等の明示指示があればそれを優先する。

## ライブラリ利用時の指示

外部ライブラリ・フレームワークのAPIを使うコードの実装/調査前に、`context7` MCP(resolve-library-id → get-library-docs)で最新ドキュメントを自発的に確認する。言語組み込み機能等の把握済み標準APIは毎回確認不要。バージョン依存の破壊的変更が多いライブラリや、最近の変更を把握していない可能性がある場合を優先する。

## 重要な決定事項の記録

設計判断・仕様変更・トレードオフなど後から参照価値のある決定事項は、作業の区切りごとにMarkdownへ記録する。記録先はプロジェクトの慣習に従い、無ければユーザーに確認するか`tmp/docs`配下を提案する。「何を」ではなく「なぜその決定に至ったか」を書き、自明な実装詳細や些細な作業は記録しない。
